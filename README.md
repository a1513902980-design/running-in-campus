# running-in-campus

> 校园跑类 App 自动化：**一套可行性方案与工程踩坑记录**。
>
> 本仓库**故意不提供可一键运行的成品**。它记录的是"这类目标在工程上有哪些环、每一环会怎么坏、
> 怎么定位"——即把一个真实项目里**与业务无关、但对任何 Windows + Android 自动化都通用**的
> 两个模块抽出来开源，其余只留方法与结论。
>
> 这个取舍是有意的：成品传出去，被目标方检索到就会直接推动反作弊升级，让所有研究者的路都断掉；
> 而方法论不会。

## 1. 问题定义与约束

这类"校园跑"App 的判定链路通常是：

```
GPS 定位 → App 端合成轨迹 → 本地校验 → 上报服务端 → 服务端复算 + 反作弊评分 → 入账
```

关键约束（决定了方案形态）：

| 约束 | 说明 | 对方案的直接影响 |
|---|---|---|
| **判定在服务端** | 客户端"通过"不代表入账；服务端会**用自己的规则重算轨迹** | 只骗客户端 UI 毫无意义，必须让**上报数据自洽** |
| **数据必须同源** | 里程、时长、均速、逐分钟速度、步频、步数之间存在互推关系 | 任何一项单独伪造都会在交叉校验里露馅 |
| **App 有反调试/反模拟器** | 检测调试端口、Root、模拟器特征、注入框架 | 裸启动会被检测；必须带完整环境伪装再启动 |
| **有可信分机制** | 被拒/异常记录会扣分，累计到阈值转人工审核 | "多跑几次碰运气"是负收益，**宁可不提交** |
| **定位源不止一路** | 无 GPS 时 SDK 会退回网络定位/缓存位置 | 这是最大的伪影来源（见 §3.2） |
| **判定点随机下发** | 每次开跑，需要途经的点由服务端随机重新生成 | 路线不能写死，必须每轮重新取点并重规划 |

**方案骨架**：不伪造"上报字段"，而是**在设备上真实地驱动定位数据源**，让 App 自己
走完整条链路生成记录 —— 这样里程/时长/步频天然同源，只有"人和设备的关系"是假的。

## 2. 整体链路与失败模式表

```
[宿主编排]
   ├─ 设备预检：时钟/时区/root/注入框架端口
   ├─ 静态资源：模拟器镜像、路网缓存、目标 App
   ├─ 路线规划：真实路网最短路 + 折返，途经点顺序校验
   ├─ 启动前预热：先喂定位，再启动 App
   ├─ 注入：环境伪装 + 定位驱动 + 上报字段接管
   ├─ 导航：UI 自动化（资源 id 优先，坐标兜底）
   ├─ 运行监控：里程/时长/自洽性，必要时动态调速
   ├─ 结束：读判定页
   └─ 提交前多道闸门：判定项 / 载荷互推 / 地理范围
```

**这张表是本仓库最有价值的部分。** 每一行都是一个真实踩过的坑：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 注入框架挂不上，脚本一条日志都没有 | 用的是调试版；**17.x 移除了内置 Java 桥** | 固定 16.x，设备侧用对应 x86_64 版 |
| 2 | 反检测直接触发 App 退出 | 注入框架监听默认端口（27042/27047）被特征识别 | 换非默认端口 + 全套环境伪装后再启动 |
| 3 | 记录时间与服务器差 8 小时，被判"数据异常" | 模拟器时区是 GMT | 强制 `Asia/Shanghai` 且关自动时区 |
| 4 | 记录被判"不在允许时段" | 宿主休眠后 guest 时钟不跟（实测漂过 4h/7h） | guest 内没有 `date -s` 权限时，只能**重启设备**让它与宿主对时 |
| 5 | 轨迹整体平移几百米、看起来"穿墙" | OSM 路网是 WGS-84，国内地图/服务端是 GCJ-02 | 规划前转 GCJ-02，喂给系统定位层时再转回 WGS-84 |
| 6 | 逐点速度与位移差 40% | **两个数据源**：轨迹积分 vs 上报字段 | 用**一条速度曲线**驱动全部输出（位移积分、上报速度、逐分钟速度、配速、步频） |
| 7 | 里程/时长/步频互相对不上 | 上报字段是"自己写的值"，与轨迹无关 | 改写**写入端（setter）**，不是读取端：上报的是 App 自己塞进对象的值 |
| 8 | 判定页显示"经过 0 个点" | 途经点判定半径很小（约 1 m），重采样会把顶点抹掉 | 把每个途径点**钉成几个精确点**；靠近时横向摆动收敛到 0 |
| 9 | 途经点顺序被判定为"提前蹭到"，那次经过无效 | 路线先经过了后面的点 | 必须校验**首次进入判定半径的里程严格递增** |
| 10 | 轨迹里混进一个 800+ km 外的点，一眼假 | 无定位时 SDK 退回网络定位/默认城市 | **喂点必须先于 App 启动** + 坐标入口消毒（§3.2） |
| 11 | 起跑瞬间坐标闪现 + 平移 | 三因叠加：消毒器把随机起点当跳变拦掉 / 两路定位源横跳 / 启动时定位层还没 fix | 见 §3.2，三种修法各有适用面 |
| 12 | 注入日志永远 0 字节，"日志有输出"是错觉 | 注入框架的 `console.log` **不走 `on("message")` 回调**，而是进独立的 log handler | 自己接 log handler 并落盘 + `fsync` |
| 13 | 明明是空的表，却"取到了数据" | 读错了表；且**整数主键**被拿去比对**UUID 外键**，永远不匹配后静默退化 | 核对真实 schema；退化路径必须打日志 |
| 14 | 多实例并发时互相覆盖 | 拼装产物是单文件，且把路线**内联**进脚本 | 每实例一份产物；一切 `workdir` 绝对化 |
| 15 | 设备上"文件明明在"却推不上去 | 用 `ls \| grep` 判断存在性——失败时 stderr 也含文件名 | 用 `test -f && echo YES` 判断 |
| 16 | 半途停跑，App 立刻上传半截记录，扣可信分 | 停止动作本身触发上传 | 只在完整跑完时才走"停止→确认"；否则直接强杀进程丢弃 |
| 17 | 判定页倒计时只有几十秒，来不及核对 | 结束页有操作时限 | 提交前核对必须在**倒计时窗口内**完成，且任何一项不过就放弃提交 |
| 18 | 换个网络/机器，脚本一排报错 | SDK 路径、设备号、端口全写死 | 路径自适应 + 环境变量隔离（每实例一套 device/port/workdir） |

> 表里第 12、14、15、18 条对应的解法就是下面开源的模块——它们是**纯工程问题**，
> 跟具体目标 App 无关，所以值得单独拿出来。

## 3. 两个通用模块

### `src/proc.py` — 受限 Windows 宿主下的子进程兼容层

**问题**：在一些受限执行环境（沙箱化宿主、AppContainer 风格约束、部分 CI）里，
**创建匿名管道会被拒绝**：

```
subprocess.run(cmd, capture_output=True)
  → PermissionError: [WinError 5] 拒绝访问。
    at subprocess.py: _winapi.CreatePipe(None, 0)
```

症状很有迷惑性：`adb` 明明在、设备也在线，脚本却报"拒绝访问"，
看起来像权限/杀软问题，其实是 `CreatePipe` 这个系统调用被拦了。
更麻烦的是它**只影响需要捕获输出的调用**，不需要捕获的调用一切正常，
所以很容易误判。

**解法**：把子进程的 `stdout/stderr` 从"管道"换成"**临时文件**"——
同一个 API、同样的语义，但不碰管道：

```python
subprocess.run(cmd, capture_output=True)   # ✗ 受限宿主必炸
proc.run(cmd, capture_output=True)         # ✓ 先试管道，炸了自动改文件
```

设计要点（都在 `src/proc.py` 里）：

- **默认先试真管道**：正常终端里行为与标准库完全一致，零回归；
- 一旦探测到 `CreatePipe` 被拒，**本进程内永久切到文件模式**，之后不再试；
- **顺带修另一个同族坑**：父进程 stdin 句柄无效/不可继承时，子进程继承它同样会
  `WinError 5` —— 所以给所有 `Popen` 补 `stdin=DEVNULL`；
- 返回值仍是 `CompletedProcess`，老代码只改一行调用。

> ⚠️ 一个真实踩过的反模式：为了"老代码零改动"而写 `subprocess.run = proc.run`。
> 因为 `proc` 内部也调用 `subprocess.run`，这会造成**自调用**，报
> `TypeError: run() got an unexpected keyword argument 'stdin'`。
> 正确做法是模块别名（`import proc` → `proc.run(...)`）或显式调用。
> 这个教训写进了模块 docstring。

自检：

```bash
python src/proc.py     # 会打印本机是否允许建管道，并跑一次子进程验证
```

### `src/geo_guard.js` — 坐标入口消毒与"双源横跳"的修法

**问题**：移动端定位在放数据进模型之前有几个经典伪影，任何一个都能让整条记录报废：

1. **退化定位**：没有真实 GPS 时，定位 SDK 会退回网络定位/上一次缓存/默认城市，
   实测会出现一个离目标区域 **800+ km** 的点，而且往往正好补记在"停止"那一刻
   —— 于是这份记录带一个一眼假的把柄。
2. **两路定位源横跳**（最反直觉）：真实注入的点与 SDK 退化点**交替**进入数据模型，
   两个点**单个看都合法**（都在合理半径内），所以只做"越界检查"根本拦不住。
   屏幕上表现为坐标来回闪现 + 平移。
3. **起跑阶段被误判**：如果消毒器用"单次位移超阈值就判假"，而它锚定的上一个点来自
   **上一轮**，那么新一轮的**正常起点**（随机撒点）会被当成跳变拦掉，
   位置被"冻"在旧点上、过几秒又放开 —— 表现为**先平移、再瞬移**。

**解法**（三层，按优先级）：

| 层 | 判据 | 作用 | 默认 |
|---|---|---|---|
| ① 越界半径 | 离中心区域超过 `RADIUS_M` 一律替换为上一个合法点 | 挡住"退化到别的城市"这类**量级**错误 | ✅ 开 |
| ② 起跑重新锚定 | **进入"跑动中"之前不判跳变**，遇到远处的新点直接重新锚定 | 修掉"正常随机起点被当假点拦掉"导致的平移/瞬移 | ⚠️ 可选 |
| ③ 保持期（防双源横跳） | 锚定一个源后，拒绝离它超过 `HOLD_M` 的点 | 挡两路定位源交替 | ⚠️ 可选 |

> ### ⚠️⚠️ 第 ③ 层有一个真实的坑：**它会把主轨迹污染成固定值**
>
> 实测事故：打开保持期后，锚点被"冻死"在起点，后续真实轨迹点走出 `HOLD_M`
> 之后**全部被当成"另一路定位源"拦掉**（日志：`通过=18` 从头到尾不变、
> `保持拦截` 累计 3600）。
>
> 后果不是"防住了假点"，而是**进入数据模型的坐标被污染成固定值**。
> 上游 App 用"坐标 × 时间"算有效运动时间，位置被冻死 ⇒ 判定"位置很久没变"
> ⇒ 时长规则误判（本例：报"超过指定运动时间"，但时长只有 17 分钟、上限 45 分钟）。
>
> **更阴的地方**：里程仍然正常增长（喂点走另一条入口，没被这一层拦住），
> 所以 **「判定页全过」和「服务端拒绝」能同时成立**，非常难查。
>
> **结论：「防伪影」的代价不能是污染主数据。** 入口消毒只该做**不改值**的判断
> ——越界就整点替换、合法就原样放过。任何"保持/冻结/平滑"都会改变 track 内容，
> 而 track 参与时长/里程/配速判定。
>
> 所以本模块默认 `STRICT_MODE = false`：**生产只开第 ① 层**。
> 真正该做兜底的地方是**提交前**——查 App 自己落库的轨迹，
> 拦在提交之前，运行期一个字节都不动。

**关键经验：**

- **阈值必须按真实采样间隔标定**，不能想当然。轨迹表里**相邻两行可以差 900 m**
  那不是假点、是采样间隔 —— 早期把跳变阈值定在 600 m 会**误杀正常轮次**。
  抓精细漂移要看连续采样表，不能看稀疏表。
- **消毒器要能自证在工作**。钩子静默失效是这个领域最贵的坑，
  所以模块里带一个**心跳**，定期打印 `模式/通过/越界拦截/跳变拦截/保持拦截/重新锚定/是否跑动中/当前合法点`
  —— 出问题时一眼能看出是"没挂上"、"在拦"、还是"拦错了"。
- **判"在拦"不够，还要判"拦对了没"**。上面那个事故里心跳显示"在认真工作"
  （保持拦截计数一路涨），但拦的是**自己的真轨迹**。
  所以心跳必须同时给出**模式**和**被放行的点数**，两个一起看才能发现异常。
- **不要跨调用缓存对象引用**（尤其 JNI/jobject），只抄标量/字符串；否则会触发
  宿主运行时硬中止，整个进程连带钩子一起没。

模块里所有常量都是占位符（`<REGION_CENTER_LAT>` 等），并且剥离了任何
"如何让上报数据自洽""如何驱动定位源"的机制——**只保留"入口消毒"这一层**。

> ⚠️ **复制这个文件到你的项目时，第一件事是替换顶部的占位符。**
> 占位符写成 `parseFloat('<...>')` 是为了让文件本身就能过 `node --check`；
> 但代价是**忘记替换会得到 `NaN`**，而 NaN 会让所有比较都为 false ⇒
> 消毒器"挂上了但一个坐标都不拦"。这正是本文档反复强调的**静默失效**。
> 所以文件里带了一个 `assertConfigured()` 启动自检：参数没配就**拒绝接管入口并大声报错**，
> 而不是安静地放过一切。（原始项目里这个坑真实发生过：钩子日志显示"已接管"，
> 但拦截计数永远是 0，排查了很久。）

## 4. 本仓库不做什么

明确列出，避免误会：

- ❌ 不提供针对任何具体 App 的可用脚本、hook 集合、签名算法、通信协议细节；
- ❌ 不提供 APK、注入框架二进制、**任何账号/凭据/token**；
- ❌ 不提供"如何生成自洽上报数据"的机制（那是这类方案的核心，也是风险最高的部分）；
- ❌ 不提供绕过反作弊/反调试的完整链条；
- ✅ 只提供：**通用工程模块**（§3）+ **失败模式表**（§2）+ 方法与结论。

## 5. 风险与伦理

- **对目标方**：这类自动化会污染体育成绩数据。本仓库的失败模式表对防守方有用，
  建议按 §2 逐条加固（尤其是第 5、8、9、10、11 条——它们暴露的是数据本身的物理合理性）。
- **对使用者**：服务端普遍有可信分与人工复核；被判定异常可能导致成绩作废、
  账号受限甚至纪律处理。**这类风险不可转移给工具作者。**
- **对研究者**：**不要把可复现的成品公开**。一次公开 = 一次反作弊升级，
  之后所有人的路都变窄。给方法、给骨架、不给可一键复现的链条，是这个领域可持续的做法。
